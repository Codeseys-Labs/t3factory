# T3 Factory

T3 Factory is a thin fork of T3 Code. It adds a Work page and a pack of workflows on top of upstream's durable workflows, and changes as few upstream files as it can. This page records why it is shaped the way it is. For what a user sees, read [Work](../user/factory.md); for upkeep, [the fork runbook](../operations/factory-fork.md).

## A task is a record, not a run

A workflow run cannot be a card on a backlog. A run summary carries no description, project, model or person, a run cannot exist before it starts, only the workflow body can set a run's tags, and the client's run list is the newest 500. So a task is a record that Factory owns, and a run is one attempt at it. A task can have many attempts; the task outlives all of them.

## Where records live

Records are JSON values in upstream's workflow key/value store, under `factory/v1/`. Agents and workflow steps can already write that store (`t3 workflow store`, `T3.store`), so they create and read tasks with no new tool. A separate database would need a new CLI command or MCP tool for each thing an agent does to a task, and each is another seam and more agent context.

[`FactoryTaskStore.ts`](../../apps/server/src/factory/FactoryTaskStore.ts) is the only place that knows the key layout. Everything else asks for tasks, attempts or notes. Moving to a real table later is a change to that file. The service builds its own key/value layer on the shared SQL client, so the board works while workflows are off; only starting needs them.

The browser never gets a storage key. It has eleven typed methods, defined in [`factory.ts`](../../packages/contracts/src/factory.ts): for tasks, subscribe, get, create, update, start and set the Orchestrator; for [Signals](#signals), list, follow a feed, stop following it, admit and dismiss. A generic `storeSet` from the browser would let any page write any key and skip every rule below. A record that fails its schema is skipped and counted, so one bad record never breaks a read.

The pack cannot import server code, and the server cannot import workflow files, so the create and start rules exist twice: in [`FactoryTasks.ts`](../../apps/server/src/factory/FactoryTasks.ts) and in [`records.ts`](../../factory/workflows/lib/records.ts). So does the union of task sources: until the pack's copy decodes a source, such as `signal` for a task admitted from a feed, the pack treats that task as missing and `factory-start` refuses it. Change one and change the other; tests on both sides (the service tests and `evals/factory-pack`) check them.

## What workflows cannot see

A workflow cannot inspect the machine's folders. So each time it starts a task, `FactoryTasks.start` looks at the task's project (a Git repository gets a `worktree`, any other folder `root`; no project means the server's scratch project) and writes the answer to `factory/v1/target/<projectId>` (`target/scratch` for no project). Only the service writes these rows. `resolveTarget` in [`records.ts`](../../factory/workflows/lib/records.ts) reads them and returns either where to work or a `problem`, which stops the run before an agent launches. A project the service has not looked at yet is taken as a worktree; a scratch task with no row stops with a message asking for a start from the Work page. If the target cannot be resolved, `start` refuses with `workspace-unavailable` and writes the same message into the row. Agents that work in a `root` folder do so under a per-project lock (`rootPool`), because they share that folder.

## Artifacts and receipts

A deliverable and the decisions made about it are records of their own: `factory/v1/artifact/<taskId>/<attempt>/<sha256>` and `factory/v1/receipt/<taskId>/<attempt>/<kind>-<sha256 prefix>`. They are not fields of `FactoryAttempt`, because a start writes that record twice (before the run starts, then again with its `runId`), so a field there would be overwritten by the second write. Both are write-once: `writeArtifact` and `writeReceipt` in `records.ts` do nothing when the key is already held, so a replayed step leaves the first record, with its first time, in place. A key holds a content hash, so a changed file is a new artifact and never edits the old one. Receipts say what was done to a hash (`sealed`, `critiqued`, `accepted`, `rejected`, `delivered`, `uncertain`, `promoted`) and by whom: `person`, `agent` or `pack`. A person's answer is told from an agent's by the session the server stamps on it, as for the merge.

## Risk tiers

[`risk.ts`](../../factory/workflows/lib/risk.ts) classifies a pull request as `low`, `standard` or `high` by the first rule that fits, from facts the host and the `scope` agent reported; a missing, duplicate or mismatched fact is `high`. `factory-task-part` ratchets the tier across fix rounds (never downgrading) and forces a person-answered merge gate whenever the tier is `high`, even with `askMerge` off. `risk.ts` has no imports, so a workflow and a plain test can both load it. The pack cannot read `factory/seams.json` at run time, so `FORK_SEAM_PATHS` copies its paths into `DEFAULT_PROTECTED_PATHS`, and `evals/factory-pack/risk.test.ts` fails when the two differ. Changing a seam in the manifest means changing that list too.

## Review ledger and outcomes

A reviewer returns findings, never a verdict. The verdict is derived from them by `deriveVerdict` in [`ledger.ts`](../../factory/workflows/lib/ledger.ts): changes are asked for exactly when a finding with a blocking severity is open. A field that lets an agent state the verdict brings back what this replaced, an approval that survives an open blocker. A stored round's verdict is derived the same way, or is `stale`.

A failed disprove never weakens the gate. A finding stops blocking only when the disprove agent returns a result for its id that says `refuted`. A missing result, an unknown id, and a step that failed or timed out all leave the finding open as `not-run`. Do not treat an unanswered finding as refuted.

Round records are write-once, like artifacts and receipts. The key is the round's address, so a replayed `ledger/<at>` step finds it held and writes nothing, and the first record keeps its first time. A stale round is stored too, as `stale`, and its one retry writes under `<at>/again`; neither is overwritten or pruned, because the Work page compares a part's rounds to say whether a finding came back. A finding's id hashes its normalised path, category and claim, so changing that normalisation breaks the comparison against every stored round. The pack cannot import the wire schema, so what it writes has to keep decoding under `FactoryReviewRound`; change one and change the other. `factory.tasks.get` leaves out a record that does not decode, as it does a damaged artifact, and returns rounds in the task detail only, never in the board stream.

An attempt's outcome record is written in the `finish` transaction with the note and its marker. It holds counts and facts, never rates, scores or thresholds: a stored rate would freeze a policy, such as what counts as a clean part, into history, and a reader can divide. Only `factory-task` writes outcomes.

`factory-task` and `factory-task-part` are at version 3 and `factory-intake` at version 2; the pack ships no earlier version of them. A run carries on at the version it started, and upstream's loader refuses a file that removes a version with unfinished runs, so the new pack is held back until runs of the old one end. An old version kept alive keeps its old rules: version 1 of `factory-task` let a reviewer's verdict decide the gate, and version 1 of `factory-intake`, with `autoStart` on, started every issue it captured, whoever opened it. Finish or cancel unfinished runs before updating a home; [the runbook](../operations/factory-fork.md#install-only-the-pack) has the steps.

## Reviews on another machine

A project's `readOnlyOn` sends the reading steps of its review rounds, `scope`, `review` and `review/…/defects`, to one linked environment; everything else runs here. Only those three may go, because the engine has no mode that both denies writes and never asks. A remote thread gets `approval-required` and `plan`, which give Codex a read-only sandbox and make Claude ask, and an approval nobody gives is a wait until `stepTimeout`. Only a step whose whole job is reading finishes unattended under that. `disprove` has to reproduce, which runs code, `plan` has no commit to pin, and the workers write, so all of them stay here, as does every `pullRequests` call, `ask` and `step`. Write denial is enforced by that machine's provider, not by the pack; do not add a step to the remote set without a mode that denies its writes there.

A remote launch names every option: a worktree at the round's pinned head SHA with `startFromOrigin: false`, both modes, the model and the project's id there. Anything left unnamed would be that machine's own default, so a round with no full pinned SHA or no model is never remote and runs here. The launch does not fetch, and if the commit vanishes from that clone after the launch checks it, T3 there starts from another base. Only the commit the agent reports catches that, so a remote lens that reports no commit, or a `scope` that reports another one, makes the round stale.

Once a round is remote there is no fallback, to this machine or to another. A failure pauses the part, or for `scope` raises the tier to `high`. Retrying there is safe, because a resume sends the same launch key and that machine answers with the thread it already made. Running the step here instead would start a second turn beside one the run lost sight of that may still be alive there, and would hide that the machine the project names cannot be used. A person moves a task back by cancelling it, removing `readOnlyOn` and starting again.

Placement reads the stored target row itself and refuses a task whose row is missing or not a `worktree`. It never takes a part's `input.target` or `resolveTarget`'s "no row means worktree" default, which would send a plain-folder project's review to a machine that has no such folder. `readOnlyOn.project` must be an id, because the engine registers a new project on that machine for a folder path; `namesFolder` in [`placement.ts`](../../factory/workflows/lib/placement.ts) mirrors the engine's `isProjectPath`, and a test pins the two together. The field is refused in the global config row, checked before decoding, because it names one project on one machine.

The pool `factory-env:<environment>` is shared by every Factory run on this server. It is taken inside the task pool, never around an `ask` or `invoke`, and never together with the folder lock, which placement makes impossible by refusing `root`; that order is what keeps it free of deadlock. It caps admissions, not live turns: a paused run gives its places back while its turn there may still run, and the pack cannot see another coordinator using that machine. The engine's step row (`environmentId`) is the evidence of where a step ran; placement adds no store key. All of this has run only against the harness's stand-in for the link, never between two machines.

## Invariants

- Task numbers are never reused. A counter hands them out inside the transaction that creates the task. Tasks are dropped, never deleted, and if the counter is unreadable the highest stored number takes its place.
- Every write to a task checks its revision. A stale revision is refused with `conflict` and writes nothing, whoever wrote: the web page, the pack, or an agent.
- A task has at most one live run. A start, serialized per task, looks at its newest attempt that has a run and refuses while that run has not ended. The attempt record is written before the run starts, and the run starts with the idempotency key `task/<taskId>/a<n>`, so a repeated start returns the same run. A crash between the two leaves an attempt without a run, which the next start reuses instead of making a second one.
- The task row is the source of truth for its lane. A run never writes `done` into the row. The board derives the column: a live run overrides it, a completed run shows Done unless a person moved the task afterwards, and a run that stopped leaves the lane alone. Anything that reads the store directly sees the person's lane, not the displayed column. The derivation is in [`workBoard.logic.ts`](../../apps/web/src/factory/workBoard.logic.ts).

The board is derived in the browser from the task snapshot and upstream's run list. A task whose run has fallen out of that list falls back to its lane.

## How a change reaches an open page

A write through the service refreshes every subscriber at once. A write by anything else, such as a workflow step or the CLI, is found by a poll: while at least one page is subscribed, the service looks at a watermark over the `factory/v1/` keys (how many rows, the latest update time, the total size of the values) and re-reads the records only when it moved. One read serves every subscriber, and a failed read is logged and skipped. Signal rows live under the same prefix, so a feed read that writes anything makes every subscribed page re-read its tasks once.

The trap: the watermark is a summary, not a version. An outside edit that leaves the row count, the latest timestamp and the total size unchanged, such as changing one letter in a title within the same clock tick as another write, is not seen until something else changes. Outside edits that change a task also bump its revision, which usually changes its size, so the gap is narrow. Do not close it by polling faster; the service's own writes never depend on the poll.

## Why agents use workflows

An agent in a thread cannot call the `t3_workflow` tool; it is hidden there. An agent uses the `t3 workflow` command. Rather than add an MCP tool, the pack exposes `factory-capture` and `factory-start` as workflows. They are durable, they take an idempotency key, and the Orchestrator skill in [`factory/skills`](../../factory/skills/t3factory-orchestrator/SKILL.md) already has the command. An `ask` is not a gate only a person can pass, because an agent can answer it with `t3 workflow signal`. The skill still forbids it. For the merge the pack goes further with `mergeNeedsPerson`: the server stamps a session on an answer given in the app and strips it from anything a sender supplies ([`workflow.ts`](../../apps/server/src/workflows/workflow.ts)), so the pack can tell an app answer from a command-line one and asks again when the session is missing. It guards against habit, not against an agent set on cheating.

## Replay safety in the pack

A workflow step can run again after a restart, so a step that creates or starts a task must not do it twice. `createTask` and `startTask` write markers (`factory/v1/captured/<runId>/<slot>`) in the same transaction as the task or attempt `runId`, and return what the first execution stored on replay. The `finish` step writes its note, the attempt's outcome record and `captured/<runId>/finish` the same way. Before merging, `pullRequestHead` records the reviewed `headSha`, and `mergePullRequest` rereads the pull request so a second run never merges twice and a push after review stops the merge (`pull request head changed after review`).

The trap: upstream's loader ([`WorkflowRuntime.ts`](../../apps/server/src/workflows/WorkflowRuntime.ts), `loadDefinitions`) reloads a changed workflow file by importing it under a new address, but a module it imports by relative path, such as `lib/records.ts`, keeps its address and Node returns the first copy. After a change under `factory/workflows/lib/` a running server fails to load the workflow or runs it against the old helper until it restarts. That includes the dev server: restart `vp run dev` after editing `lib/`.

The pack's rules for checking that a pull request is the project's, binding merge to the reviewed `headSha`, and enforcing person-only merge live once in [`records.ts`](../../factory/workflows/lib/records.ts). Every workflow that merges, whether a task's part or an upstream sync, must go through them.

## Intake starts only trusted authors' issues

Anyone who can open a labelled issue can have it captured; starting is narrower, because a started task puts agents with tools to work on what the issue's author wrote. So `autoStart` starts an issue only when a GitHub login in the binding's `authors` opened it after intake began. An absent or empty list starts nothing, and a binding stored before the field existed decodes as having none, so the upgrade fails closed: existing `autoStart` bindings capture but stop starting until someone lists authors. Do not make an absent list mean everyone.

Only a GitHub row's login counts as an identity; other trackers put display names or bot names in that field. Both sides must match GitHub's login shape before they are compared, and only then without regard to ASCII case: lower-casing unchecked input would let `\u212Ait`, whose Kelvin sign folds to `k`, match a listed `kit`. The check is made once, when the issue is listed, and later edits are not checked. A listed account is a principal, not proof that a person wrote the text, so an account that relays text from elsewhere must never be listed.

The time intake began is its own key, `factory/v1/intake-since/<projectId>`, written once by the live tick in a transaction that rereads the binding; the pack never writes the binding. The binding is the person's row, and `store set` replaces a whole value, so a time kept inside it would be erased or moved by their next edit, and a pack write would race it. Nothing moves the stamp afterwards: disabling and enabling keeps it, deleting it makes the next tick stamp a later time, and nothing backdates it, so issues open when intake began never start by themselves.

`factory-intake-preview` is a workflow of its own, not a flag on the tick, so it can never stamp, capture or start. It writes nothing to the store and never calls `stop`, because `factory-self-repair` counts stopped runs. Issue keys that appear twice in one listing, which several repositories in one project can produce, are refused; a collision across listings is not detected, so a repository's `#12` seen earlier hides another's later `#12`.

## Signals

A signal is an observation. `factory-signals` reads followed feeds and writes only `signal-state/` and `signal-candidate/` rows; it starts no agent and writes no task. The only path from an item to a task is `factory.signals.admit`, which a person calls (a client with the operate scope counts as one, as it does for start), and it starts nothing. Anything that made or started work from a feed by itself would let whoever controls the feed direct agents.

Feed text never enters a task's description, because `factory-task` puts the title and description into the planner's brief, and a feed's text is written by its publisher. The admitted task's description is fixed text naming the feed's label, which a person typed, and the candidate's id, revision and digest; the summary and link stay in the Signals dialog, and links are never fetched or rendered as links. The one exception is the title: one normalized line of at most 200 characters that a person read before admitting. It still reaches the planner's brief and the thread title, so it can carry an injected instruction, which the description cannot. Normalization therefore removes every character a person cannot see (control, format, private-use, unassigned and lone-surrogate code points, variation selectors and Hangul fillers), so the text that was read is all the text there is; it also caps a run of combining marks at 30, before and after NFC, which keeps NFC linear on hostile input and the result stable when normalized again. A stored title that is not one normalized line is refused as damaged, not cleaned, because the digest covers it and the person decided on the text as shown.

An admitted candidate is its own receipt. The row in state `admitted`, holding the revision, digest and task it was admitted as, is the only record that the item became a task, so admitted rows are never pruned while their feed is followed: pruning one would turn a rediscovered item into a new candidate, and a second Admit into a second task. Every decision names the revision and SHA-256 the person saw, and every branch that returns an earlier decision compares both first; an admit retry answers only with the task whose source names that candidate and digest. `factory.tasks.create` refuses a `signal` source, so nothing else can make one. Removing a feed deletes its rows, admitted ones included, so following the same address again can admit an item a second time.

The address rules run when a feed is followed (the server) and again at every pull (the pack). The pack cannot import the server, so the address check, the text normalization and both digests exist in [`FactorySignals.ts`](../../apps/server/src/factory/FactorySignals.ts) and in [`lib/signals.ts`](../../factory/workflows/lib/signals.ts), and the pack copies the wire's numbers; change one and change the other. At pull time every resolved address must be public or the whole answer is refused, and the connection is made to the checked address under the host's TLS name, through no proxy and following no redirect. That stops DNS rebinding between the check and the connect, and a valid certificate for the name is still required. It does not stop a public address that routes to a private service, such as a proxy, a NAT rule or a load balancer in front of an internal host; only the network's egress rules can refuse that.

The hourly cooldown reads the server clock inside the pull step, never the tick's `scheduledAt`, which whoever starts a tick supplies, so a hand-started or backdated tick cannot pull sooner. A pull commits its `lastPullAt` before any network I/O: a replayed step finds its own reservation and does not fetch again, and a feed that fails or crashes mid-read still waits out its hour. A clock that moved back makes a feed due rather than stopping it for good. A damaged state row is never overwritten; its feed is reported `store` and is not read until a person removes it.

The pack parses feeds itself because a workflow file can import only Node built-ins and an installed pack is copied files with no package beside them, so the lockfile's XML libraries cannot be reached from there. Its extractor makes one pass, bounds every name, attribute, reference and nesting depth, and refuses DTDs and entities. Replacing it with a dependency would not load in an installed home.

## Keeping up with upstream

Every edit to an upstream file is a possible conflict on every merge, so each is counted and capped. [`factory/seams.json`](../../factory/seams.json) lists the files Factory owns, the upstream files it may edit by hand (the seams, at most twelve, each with a `maxAdded` line budget), and the generated files. [`scripts/factory-seams.ts`](../../scripts/factory-seams.ts) compares `HEAD` with its merge base and fails on any other change, on a deleted or renamed upstream file, on a seam exceeding `maxAdded`, and on a seam that no longer differs. A seam edit is small and mechanical: an import, a registration, an entry in a list; anything larger belongs in a Factory-owned file that the seam calls. The service is read in `ws.ts` through `FactoryTasks.orDisabled`, which needs no context, so upstream's own tests of that file stay untouched.

The seams together also have one budget, `maxAddedTotal` in `seams.json`. A twelfth seam, or a larger cap, is admitted only when a zero-seam design fails on a named missing upstream API, the seam adds registration lines only, and it says when it can be removed.

Generated files are regenerated after a merge, never merged by hand. Translation catalogs are the exception that needs a tool. Taking upstream's catalogs and running the generator resets every Factory string to English, and upstream's `i18n:check` still passes. So Factory's translations live in overlay files and [`factory-i18n.ts`](../../scripts/factory-i18n.ts) rebuilds each catalog as upstream's plus the fork's keys.

The fork adds no dependencies, so the lockfile stays upstream's, and CI checks it.

## Pinned third-party assets

[`factory/vendor/manifest.json`](../../factory/vendor/manifest.json) pins CLIProxyAPI and its Management Center, the pair a later stage is to bundle, by exact version, URL, size and SHA-256 for each file and its licence text. [`factory-vendor.ts`](../../scripts/factory-vendor.ts) checks the manifest and downloads exactly those bytes. Nothing runs, unpacks or installs them yet, the pack installer does not copy `factory/vendor`, and the pin says nothing about whether the pair works together or keeps its keys apart: the stage that runs them has to test both on these bytes.

Neither publisher signs its releases. CLIProxyAPI rebuilds its `checksums.txt` after a release is published, both projects' releases can be edited, neither has a signature or attestation, and the console's tag commit is unsigned. So the hashes are trust on first use: they are what was downloaded when the pin was made, and they catch any later change to those bytes, not bytes that were already bad then. To narrow that, a pin is accepted only for a release that was at least 168 hours old when its bytes were retrieved, so a bad release has had a week to be noticed and withdrawn before it is taken. Age does not authenticate bytes. The pin is the newest release that passed at the time it was retrieved, not a constant, and moving it is a hand edit followed by a `fetch` that proves it.

"Pinned" means the exact URL: the release-download or tag URL that the component's repository and version imply, compared as a string, so a `latest`, branch, query, port or case variant cannot point at bytes that move. The tool follows redirects itself and checks every hop, and the only host a redirect may add is GitHub's release-asset host. `fetch` writes only into a folder it creates, never overwrites a file, and after any failure removes everything that run created, so a folder holds the whole verified set or does not exist, unless the process was killed or a removal failed, which it reports.
