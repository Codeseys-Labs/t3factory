# Linear UX comparison and T3Factory decision

Research date: 2026-11-04. Recommendation for the next desktop design pass; no application behavior or integration has been implemented. “Current Linear” below means official public documentation and published images retrieved today, not a logged-in product inspection. Images can lag the shipped application. Proposed T3Factory behavior is explicitly a design recommendation.

## Decision

Keep Factory's planning/source/execution separation and its native T3 shell. Adopt Linear's clearer scope, view controls, issue identity and progressive disclosure. Prioritize the ability to tell **which record an action changes** before adding synchronization. A Linear issue, Factory planned item and execution invocation remain separate records. A finished agent run must never, by itself, mark an issue Done.

## Prioritized changes

**P0 — D01: Make scope and identity persistent.** Above Work, add labeled local scope and a separate `Linear workspace / Team / Project` scope control when connected. Allow All accessible teams and No project; do not nest all projects underneath a single team. Show source badge + `ENG-123` + title in rows and inspector headers, with Copy ID, Copy link and Open in Linear. Keep Factory plan ID secondary but accessible even after removal. Local T3 project, Linear project and Linear team must never be interchangeable selectors. Changing browsing scope must not move the issue.

**P0 — D02: Name every state and mutation destination.** Keep three compact labeled fields: Planning stage, Linear status and Execution. The planning board defaults to **Group: Planning stage**, never a generic Status label. A Linear status editor loads the selected team's states and offers `Update in Linear`; moving a card between planning columns changes only the Factory stage. A future Group: Linear status board must explicitly identify upstream writes and prevent ambiguous cross-team drops. “Blocked” is a relation, “Held” a delivery condition, and execution failure is an execution outcome. Preserve acceptance and delivery as independent decisions.

**P0 — D03: Keep local Intake separate from Linear Triage and personal Notifications.** Use distinct destinations/queue labels, counts and actions. Retain Add to plan and Defer this revision for local admission. In a connected Linear Triage view, show Accept in Linear, Decline in Linear, Mark duplicate in Linear and Snooze in Linear, with a preview of the affected issue and outcome. Adding to a Factory plan must not silently accept Linear Triage. A local defer must not silently snooze the team queue. Marking a notification read must not remove intake, change status or stop work. Start with visible actions; defer numeric destructive shortcuts.

**P1 — D04: Separate view controls.** Keep Board/Table/List; place Filter and Display beside them. Display initially offers Group (Planning stage, Linear status, assignee, project, none), Order, Properties and empty groups. Put editable applied-filter chips below the toolbar, with result count and Clear filters; include source, team/project, planning stage, upstream status, execution and relation filters. Switching layouts preserves scope, filters, ordering and selected record. Preferences are personal by default; Save shared view is explicit. Expose whether Triage and removed items are excluded. Start with basic conditions, not an AI filter builder or nested query designer.

**P1 — D05: Recover scan space and deepen detail progressively.** Keep the T3 conversation sidebar. Provide an inspector-closed default for a saved scan view, compact selection inspector and explicit Open details action. Target a 340–380px inspector at 1600px, validating readability rather than shrinking text. At 1280px use a dismissible detail overlay/full reader so cards retain the established readable width. Keep title, source identity, labeled states, blockers and the appropriate Open thread / Review & evidence / Run workflow action visible. Move revision history, exact pins and repeated authority explanations into named disclosures. Required warnings stay visible at the action. Full reader places description, acceptance context, sub-issues and activity in the main area; properties and artifact links sit beside it. Do not adopt Linear's colors, typography or shell.

**P1 — D06: Make relations navigable and directional.** Replace the single prose related-work treatment with sections for Parent, Sub-issues, Blocks, Blocked by, Related and Duplicate of, showing counts and linked identities. Retain “possible match” as a suggestion until confirmed. Never turn exact-source lookup, similar titles or a shared PR into identity equality. Duplicate requires selecting the canonical issue and reviewing upstream effects; local admission history remains available. On a collapsed row show a blocker indicator with accessible text. Support removing a relation and returning to the original filtered selection.

**P1 — D07: Define keyboard and disclosure contracts.** Proposed Factory bindings: arrows move focus, Enter opens detail, Space peeks, Escape closes the topmost transient surface and restores focus; nested Escape then clears selection. Add Filter and Display commands with visible shortcut hints, and command-menu equivalents for selection actions. These are proposals subject to existing T3 shortcut conflict review, not verified current behavior. Disable single-letter actions while typing; all hover/context actions need focusable visible alternatives. Disclosures expose expanded state; dialogs restore their invoking focus. Do not auto-start execution on selection, Enter or a layout switch.

**P0 integration prerequisite / D08: Show pending writes and reconciliation.** Proposed edits to Linear show destination, pending state and confirmed result; failure retains the draft and offers retry. If the remote record changed, show current remote value versus proposed value rather than overwriting silently. Keep the latest remote snapshot separate from the revision pinned to an admission or invocation. Reconnect/reconcile must not make duplicate planned items or duplicate issue edits. Show access lost / unavailable distinctly from deleted. OAuth, GraphQL mutations and webhook-fed updates are official building blocks; they do not themselves establish a conflict policy. [Linear API](https://linear.app/developers/graphql)

## Integration mapping policy

These are proposed ownership rules, not a verified schema or runtime contract:

- Bind a remote issue by connection/workspace plus API issue UUID; store identifier and URL as changeable presentation fields. Bind the Factory planned item by its own ID and the reviewed source snapshot separately. Team moves update display identity and trigger scope/status reconciliation rather than creating a second plan.
- First bidirectional slice: title, description and explicit upstream status edits, with remote confirmation. Assignee, project, priority, labels and relations may be read first; enable writes only after exact per-field mappings and removal semantics exist. Preserve unknown upstream values. Comments, attachments and parent-status automations stay out of this first slice.
- Status mapping is per external team/state ID. A mapping may be intentionally absent. No automatic Ready→Todo, execution Working→In Progress, execution Complete→Done, or delivery Held→Blocked mapping. A separately configured automation would need its own visible trigger and authority.
- Plan removal means remove membership only; issue deletion, duplicate resolution and closing are separate upstream operations. Outbound changes and inbound updates need origin/deduplication handling and a reconcile path; no guarantee of webhook order or exactly-once behavior is assumed here.

## Currentness caveats and bounded next step

The current canonical [Triage page](https://linear.app/docs/triage#take-actions) says 1 accepts, 2 declines, 3 marks duplicate. A parameterized/search-indexed variant still gives the older 2/3 ordering. The [official changelog](https://linear.app/changelog) corroborates the new order. More materially, Triage text describes duplicate as Canceled while [Issue properties](https://linear.app/docs/issue-property#duplicate-issue-status) specifies a reserved Duplicate status. Prefer the latter for explanatory UX, but use actual returned state metadata/results when implementing; never encode Duplicate as ordinary Canceled based on the older passage. The generic Display page also says Inbox grouping is unavailable while the dedicated Inbox page mentions a preferred grouping: exclude Inbox grouping from the proposed first slice.

Revise only three desktop compositions next: Work scan with Display/Filter open, selected-item detail with upstream status edit, and Intake with explicitly local versus upstream actions. Reuse them for these five checks rather than creating a new scene matrix:

1. Board→List→reader→Back preserves selection, scope and query; a filtered-out selected record has an explicit explanation.
2. A planning-stage move and an execution completion leave Linear status unchanged; a confirmed Update in Linear changes only its intended upstream fields.
3. The same issue moved to another Linear team retains the local association despite a new human identifier; incompatible status/project mappings require resolution.
4. Add/defer/read-notification/Linear accept have distinct effects; duplicate direction and relation removal are inspectable.
5. Pending/error/conflict/access-lost states are distinguishable; keyboard focus returns correctly and no navigation action dispatches work.

This is a decision-ready design recommendation. Native keyboard, responsive behavior, actual API permissions/schema details, synchronization and provider behavior remain future verification work.
