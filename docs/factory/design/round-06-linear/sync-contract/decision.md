# Linear ↔ T3Factory: bounded sync contract decision

Status: proposed research contract, not implemented or runtime-qualified. Researched 2026-11-04 from official Linear documentation and published SDK source. `mapping.json` is the companion machine-readable proposal; its example IDs are fictional and its deployment is disabled.

## Decision and MVP boundary

Implement one Linear integration, owned by one T3 environment, connecting one Linear organization and one selected team to one environment-local T3 project. Optionally narrow intake to one Linear project UUID. Import existing and new issues as source records in Intake; a person explicitly adds a source to the plan. Bidirectionality means **Linear issue observations into T3, explicit source-status changes from T3 into Linear, and an opt-in T3-owned backlink attachment**. It does not mean unrestricted two-way editing of every field.

Linear owns issue content and human ownership. T3 owns plan membership, planning stage, workflow binding, execution history, review, acceptance and delivery. Source-status editing is a separate command labeled with the Linear destination, exact team status and latest observed value. Board stage movement never writes `stateId`; incoming Linear status never moves the planning stage or starts/stops an agent. No automated issue creation, comment mirroring, assignee writes, relation synchronization, deletion propagation, cross-environment failover, or AgentSession execution in this MVP.

This preserves the supplied desktop design (archived evidence: `../../round-05/refinement-01/final-desktop-design.md`): lines 17–23 separate planning, source and execution, preserve removed membership/history, distinguish admission from execution, and keep acceptance/delivery separate. Lines 54–58 explicitly exclude runtime qualification and webhook-failure evidence. Reading that file did not involve Figma or browser automation.

## API choice and evidence

Use the public [GraphQL API](https://linear.app/developers/graphql) at `https://api.linear.app/graphql`, with the official [TypeScript SDK](https://linear.app/developers/sdk) where convenient. Use narrowly selected GraphQL queries for reconciliation to avoid SDK relation-by-relation fetching. SDK connections expose cursors; obtaining `.nodes` once does not fetch the entire collection. HTTP 200 alone does not establish GraphQL success. [SDK data operations](https://linear.app/developers/sdk-fetching-and-modifying-data), [rate limiting](https://linear.app/developers/rate-limiting).

Published source inspected: [SDK schema at commit 9ba7b299eb5fb0036d14d2e8299e18e7c4bd13e3](https://github.com/linear/linear/blob/9ba7b299eb5fb0036d14d2e8299e18e7c4bd13e3/packages/sdk/src/schema.graphql), fetched through public HTTP, not Git. Its [package.json](https://github.com/linear/linear/blob/9ba7b299eb5fb0036d14d2e8299e18e7c4bd13e3/packages/sdk/package.json) reports `@linear/sdk` `101.1.0`; this is the repository version inspected, not a verified installed or npm-latest version. No authenticated live introspection was performed; verify selected operations against the deployed schema before implementation acceptance.

### Built-in issue sync is precedent, not a generic sync service

Linear's [GitHub integration](https://linear.app/docs/github#configure-github-issues-sync) supports team/repository issue synchronization, distinguishes it from PR-driven status automation, requires explicit historical import, and limits comment sync to a designated thread. Its [Jira integration](https://linear.app/docs/jira#synced-properties) uses account connections for identity mapping, leaves unmappable statuses unchanged, and does not cascade issue deletion. These product-specific rules are not guarantees for custom applications.

The inspected schema exposes `Integration`, vendor-specific operations, and `integrationSyncResourceIds(integrationId)`. `Issue.syncedWith` exposes external provenance; its `ExternalSyncService` enum currently lists `github`, `jira`, `slack`. This is not evidence of a public API to register an arbitrary T3Factory issue-sync backend or obtain Linear-managed deduplication/conflict resolution. Use normal issue/attachment operations and own this bounded contract. Never fabricate a Linear `Integration.id` or write built-in sync metadata. If an issue is already synced to GitHub/Jira, display that fact: an explicit Linear status write may propagate through those integrations. Disable T3 source-status writeback for such issues by default until the connection owner explicitly permits that interaction. An empty `syncedWith` does not establish exclusive ownership: PR status automations, team automations and human clients may still write the same issue.

### Conditional updates: investigated, not assumed

The inspected schema defines `issueUpdate(id: String!, input: IssueUpdateInput!): IssuePayload!`. `IssueUpdateInput` contains field assignments, including `stateId`, but no expected revision, expected `updatedAt`, compare predicate or `clientMutationId`. `IssuePayload.lastSyncId` is output, not an accepted update precondition. Official API/SDK documentation and targeted official-site searches did not establish `If-Match`/ETag CAS, a generic idempotency-key contract, or exactly-once issue mutations. **No documented server CAS was found; this is not a claim about all undocumented backend behavior.**

Consequently, pre-read → compare → mutation → readback is only best-effort conflict detection. A local database version check protects local state; it cannot lock Linear. GraphQL mutation sequencing does not make our pre-read and write a transaction against other clients.

Concrete race: T3 reads state A; a human changes A→B in Linear; T3 sends A→C and overwrites B; readback sees C. Readback can show convergence without discovering the lost intermediate human edit. A received webhook's previous values may expose it, but missed delivery prevents guaranteed detection. Do not promise lossless concurrent status editing. If the product requires that guarantee, disable outbound source-status edits and retain Linear-owned status plus the T3-owned attachment, or obtain a documented conditional API from Linear first.

## Identity and entity mapping

| Linear identity                              | Proposed T3 representation                                         | Rule                                                                                                                                         |
| -------------------------------------------- | ------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `Organization.id`                            | Connection's `linearOrganizationId`                                | Verify after OAuth and bind every resource/receipt to this tenant. Workspace slug/name is display only.                                      |
| `Team.id`                                    | Explicit intake scope and state-map namespace                      | A team is not a repository or environment. No team-name matching.                                                                            |
| `Project.id` (nullable on issue)             | Optional source grouping/filter                                    | Not T3's filesystem project. Its rename does not rebind the T3 workspace.                                                                    |
| `Issue.id` UUID                              | `sourceRef = linear:{organizationId}:issue:{issueId}`              | Canonical external identity. `identifier`, number and URL are cached display/navigation values; refresh after moves.                         |
| `(environmentId, projectId, sourceRef)`      | One local source binding, zero or one retained planned item in MVP | Intake alone creates no plan membership. Remove/restore updates membership on the same retained item; never creates a second external issue. |
| `WorkflowState.id` with team ID              | Exact `sourceState` plus optional mapped source category           | Never use name, order or category alone as the mutation target.                                                                              |
| `User.id` / issue `assignee.id`              | Linear human-assignee reference                                    | Do not equate with OAuth installer, T3 operator, workflow owner or provider account. No email/name auto-linking.                             |
| `Issue.delegate.id`                          | Observed agent delegate reference                                  | Separate from human assignee; read-only and non-executing here.                                                                              |
| Attachment ID and `(issueId, canonical URL)` | Optional backlink binding                                          | Link identity survives reconnection. Do not infer issue identity from attachment title.                                                      |
| Thread, invocation, candidate and delivery   | T3-only references                                                 | One issue may accumulate multiple executions; none is the issue's identity. No `AgentSession.id` alias.                                      |

One designated environment writes. Other devices use its normal authenticated client connection. Copies of its database must not become writers. Reauthorization replaces credentials, not source identities. A different organization cannot inherit existing bindings. Owner migration requires explicit handoff with the former writer quiesced; uncertain old writes keep writeback held. This is a scope restriction, not a distributed lease system.

## Per-team WorkflowState mapping

Discover and paginate each selected team's states, retaining `id`, `name`, `type`, `position`, `archivedAt` and `team.id`; preserve inherited-state identity when supplied. The schema uses a string type, currently documenting `triage`, `backlog`, `unstarted`, `started`, `completed`, `canceled`, `duplicate`. The [issue properties guide](https://linear.app/docs/issue-property#issue-status) confirms team-specific workflows and a system-managed Duplicate status.

| Linear type                                | Proposed source category | Planning/execution effect                                             | Outbound policy                                                            |
| ------------------------------------------ | ------------------------ | --------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `triage`                                   | `triage`                 | None; T3 Intake membership is independent                             | Explicit mapped team-state selection only                                  |
| `backlog`                                  | `backlog`                | None                                                                  | Same                                                                       |
| `unstarted`                                | `unstarted`              | Does not mean the item is admitted or Ready                           | Same                                                                       |
| `started`                                  | `started`                | Does not prove a provider is running                                  | Same; In Progress and In Review can have different IDs with this same type |
| `completed`                                | `completed`              | Does not accept a candidate, merge, publish, or release delivery Held | Same; explicit reopen uses an exact eligible nonterminal state             |
| `canceled`                                 | `canceled`               | Does not stop or fence a remote writer                                | Same                                                                       |
| `duplicate`                                | `duplicate`              | Retain source/history; no silent alias/merge of plan items            | Read-only; duplicate relationship creation is out of scope                 |
| Missing, new unapproved ID or unknown type | `unmapped`               | Show raw state and mapping attention; keep plan unchanged             | Hold status writes; never fall back to the first state                     |

Approve the mapping by `(organizationId, teamId, stateId)` with a local mapping revision. Types suggest grouping, never a Ready→first-unstarted conversion. Labels may change without changing identity. An archived/deleted target, changed type or team move invalidates queued state commands. Refresh on setup/reconnect, before a write, on unknown-state observation and during metadata reconciliation; do not assume a dedicated WorkflowState webhook is available. A new ID with an old name is still unmapped. A fetched live row must agree with the approved ID/team/type before it can be offered as a write target.

Example: Team A has A1=In Progress and A2=In Review, both `started`; Team B has B1=In Progress. Import A2 exactly. An inverse `started` lookup cannot pick A1, and A1 is invalid for Team B. `mapping.json` includes distinct fictional UUIDs, a reserved Duplicate row and an unapproved custom state. Only one team is enabled in the MVP; a move outside that team becomes `out_of_scope` until explicit reconfiguration and mapping approval.

## Field ownership and conflict recovery

| Fields                                                                                                             | Owner / write direction                                                 | Recovery policy                                                                                                                                                |
| ------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Title, Markdown description, human assignee, priority, labels, due date, cycle, parent/relations, project and team | Linear → source snapshot; MVP need only hydrate selected display fields | Refresh source; never rewrite from old T3 copies. Keep any local notes separate. Unknown user/label IDs remain unresolved references, not cleared fields.      |
| Source `stateId`                                                                                                   | Linear canonical observation; explicit T3 command permitted             | Per-field baseline comparison, minimal `stateId` patch, mutation result and readback; hold conflicts/ambiguous results.                                        |
| Plan membership/stage, local notes, bindings and execution/acceptance/delivery                                     | T3 only                                                                 | Linear updates cannot mutate these. Content changes do not rewrite a running workflow's pinned source snapshot.                                                |
| Opted-in backlink title/subtitle/metadata                                                                          | T3 → its attachment only                                                | Publish minimal planning summary and observation time. Unexpected remote edits/deletion hold publication; do not fight a human by recreating it automatically. |
| Archive/trash/delete availability                                                                                  | Linear → source availability                                            | Preserve local provenance, hold outbound writes, recover by re-read; no cascade.                                                                               |

Proposed status-command record: command UUID, owner environment, connection epoch, organization/issue/team IDs, mapping revision, reviewed source fingerprint, baseline `stateId`, desired `stateId`, T3 operator ID and optional verified Linear-user reference. Queue at most one unresolved status command per issue and serialize local read/apply operations. Re-read access, current team/state and mapping immediately before sending. A changed title alone refreshes the source but does not conflict with a status-only edit; a changed state does. Identical desired/current state is `already_observed`, not proof our mutation ran. Record both requested and observed state separately.

On detected conflict, show baseline/current/requested values with times and origins. Offer **Use Linear** (discard local intent) or **Review and submit again** (new command against a new baseline). Never silent last-writer-wins, inverse writes or automatic rollback. A nonterminal state change explicitly requested in T3 can reopen the source; it does not restore removed plan membership or restart execution.

A transport timeout/5xx after send is `outcome_unknown`, not failed-with-no-effect. Read current state. If desired is observed, close as `desired_observed` with uncertain attribution; if different or unreadable, retain the conflict/unknown outcome. Do not blindly resend the stale status command. Even a later read of the old value does not prove an earlier request cannot still commit. A renewed human command must disclose that uncertainty; local cancellation or a new local fencing token cannot cancel a request already inside Linear.

## Idempotency and echo suppression

Proposed local inbox uniqueness is `(connectionId, webhookId, Linear-Delivery)`; a payload hash is audit evidence, not a replacement identity. Durable receipt and scheduling the reconciliation work commit before acknowledgment. Duplicate receipts can return success without reapplying. Also make snapshot application value-idempotent so duplicate payloads with different delivery IDs do no work. Store local command IDs and outcomes durably across restart; no browser tab owns the queue.

Treat webhook events primarily as invalidations: fetch current canonical issue state, then apply through the same serialized per-issue path used for readback. Keep changed-field information for audit. Suppress only an exact expected field echo associated with a pending/recent command; still ingest unrelated human changes in that event. Actor equality is merely supporting evidence: ignoring all app-actor events would lose changes from another installation or another operation. Equal timestamps with unequal content require refresh/conflict handling, not tie-breaking by local clock. Incoming refreshes never enqueue outbound commands, which structurally prevents mirror loops.

Linear explicitly documents attachment upsert behavior keyed by issue plus URL. Use one stable URL and current desired payload for retries of this single owned attachment; do not add comments as a side effect. This avoids duplicate attachments, not stale overwrites or exactly-once delivery. A late old request can still replace newer content, so keep one in flight and reconcile unknown outcomes before sending a later revision. [Attachments](https://linear.app/developers/attachments).

Issue/comment creation is deferred. Their published create inputs allow client UUIDs, but duplicate-ID success/replay semantics are not documented here; that is not a generic idempotency guarantee. A later create feature must persist its UUID before send, query/reconcile unknown outcomes, and never choose a fresh UUID merely because a response was lost.

## Pagination, reconciliation and lifecycle

Linear list queries use cursors; continue until `hasNextPage=false` using `endCursor`, with explicit `first:50`. This applies independently to teams, states, issues and nested labels. Archived records require `includeArchived:true`. The API supports ordering by `updatedAt`; filters support date bounds. [Pagination](https://linear.app/developers/pagination), [filtering](https://linear.app/developers/filtering), [archived resources](https://linear.app/developers/graphql#archived-resources).

Proposed reconciliation procedure:

1. Enable durable webhook receipt before the initial baseline scan where public ingress exists. Record scan start and paginate the selected team, including archived issues. Upsert source identity; do not automatically add or restore plan membership. Mark bootstrap incomplete until all pages succeed. Drain queued invalidations afterward.
2. Periodically query a bounded update window, `updatedAt >= previousCompletedUpperBound - 10 minutes` and `<= thisScanUpperBound`, using server-side team/project filters and `orderBy:updatedAt`. Ten minutes is an MVP overlap choice, not a Linear guarantee. Persist page cursor/window for crash recovery; advance the completed watermark only after the entire window commits. On invalid cursor restart that window and deduplicate by issue UUID and content.
3. Polling pages are not a point-in-time snapshot. Concurrent updates can move rows across cursors and window bounds. Use overlap plus a periodic full scoped reconciliation; no finite overlap proves no missed updates under arbitrary delay. Show last completed reconciliation and degraded freshness. Proposed cadence: webhook mode, 15-minute incremental repair and daily full sweep; local polling-only mode, 5-minute incremental repair while online and a full sweep on reconnect. Adapt to quota and dataset size; these are product defaults, not API SLAs.
4. Compare known bound IDs against inventory. Batch lookup missing bindings by UUID without the old team/project filter to detect moves or access loss; use individual issue reads only for unresolved exceptional cases, not polling every issue. A page omission, null, partial GraphQL error, permission denial or failed scan is **not deletion proof**. Large inventories may need several bounded batches.
5. Honor `Retry-After`, request/complexity limits and GraphQL `RATELIMITED` responses. Keep watermarks unchanged on partial failure; pause writeback on revoked access and surface reauthorization. [Rate-limit behavior](https://linear.app/developers/rate-limiting#handling-rate-limited-errors).

Archive is availability, not source completion. Trash/deletion, archive and plan removal are different operations. Linear documents restoration of deleted issues during its trash retention period and separate archiving behavior. [Delete and archive](https://linear.app/docs/delete-archive-issues). On observed `archivedAt`, retain the source and pin history, mark archived and hold writes. On authenticated Issue `remove`, record an external-removal tombstone and hold writes; do not claim permanent deletion. `trashed:true` is likewise separate from workflow state. If the same UUID becomes accessible and live again, update availability; do not restore plan membership or replay old commands. Unknown inaccessible issues stay `missing_or_inaccessible`, with last known values clearly stale. Hard deletion never causes automatic issue recreation. No T3 action deletes, trashes, archives or unarchives a Linear issue in the MVP.

## OAuth, human identity and optional agents

Choose `actor=app` for the environment-owned service connection. Actions are attributed to the app; the installing admin is not the assignee. `actor=user` is a different per-user authorization model, not impersonation of the person who clicks a T3 button. `createAsUser`/avatar are display attribution on supported creates, not delegated authorization. [Actor authorization](https://linear.app/developers/oauth-actor-authorization).

Request `read,issues:create`; current docs explicitly describe `issues:create` as allowing issue creation/update and attachment creation. No comment writes are needed. Use PKCE S256 and state bound to the pending T3 environment installation. Persist rotating access/refresh credentials in the environment's credential store, not clients or source records, and serialize refresh. Current OAuth documentation specifies 24-hour access tokens and a 30-minute refresh replay grace period. Prefer returned expiry rather than hardcoding it. [OAuth](https://linear.app/developers/oauth-2-0-authentication).

An app installation has a workspace-specific `viewer.id`; retain it beside organization and OAuth client IDs. `actor=app` cannot request `admin`. Configure webhooks in the OAuth application's settings, or have a workspace admin configure them; do not propose `actor=app,scope=admin` followed by `webhookCreate`. Team permissions can change. Reauthorization must verify the same organization and selected team. [App authentication](https://linear.app/developers/agents), [webhook setup](https://linear.app/developers/webhooks).

Linear's optional AgentSession/AgentActivity system is a separate product capability. `app:assignable` permits agent delegation, which sets `delegate`, preserving human `assignee`; `app:mentionable` is also optional. Do not request either scope or subscribe to AgentSession events here. Those events can create session UI immediately, use `created`/`prompted` actions, and expect activity/external-URL acknowledgment rapidly. An eventual adapter would bind organization + AgentSession ID to explicit T3 admission/invocation records and implement stop/failure semantics separately; it cannot reuse a status webhook as execution authority. [Agent setup](https://linear.app/developers/agents), [Agent interaction](https://linear.app/developers/agent-interaction).

## Public ingress on remote and local T3

Documented webhook delivery: public HTTPS, non-localhost endpoint; HTTP 200 within five seconds; failed deliveries have at most three retries after one minute, one hour and six hours, and persistent failure may disable the webhook. `Linear-Delivery` identifies a payload. Validate raw-body HMAC-SHA256 and the signed body's `webhookTimestamp` freshness (Linear recommends one minute). `updatedFrom` carries previous changed values. No ordered, gap-free or exactly-once delivery guarantee was found. [Webhooks](https://linear.app/developers/webhooks).

Use the [SDK webhook verifier](https://linear.app/developers/sdk-webhooks) or equivalent raw-byte validation; impose a body-size bound and validate signature length before constant-time comparison. Verify timestamp when first receiving at public ingress, not again hours later when replaying an authenticated durable internal receipt. Do not loosen signature checks to repair missed events; reconcile through GraphQL. Never acknowledge before durable storage. If storage is unavailable, fail delivery rather than pretending it was accepted.

For this MVP, use a self-managed OAuth app configuration per owning environment, with one selected organization/team connection. This avoids inventing a shared SaaS routing/secret-distribution service. Application-level webhooks can be broader than the selected team: route by installed organization, then enforce local team/project scope, while still reconciling already-bound issues that move out of scope.

| Deployment                                                   | Decision                                                                                                                                                                                                                                                                       |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Always-on remote T3 with configured public HTTPS             | Dedicated proposed `/integrations/linear/webhook` route behind TLS ingress, authenticated by Linear signature rather than a browser session. Only that route is publicly admitted; normal T3 RPC/auth remain protected. Persist inbox before 200, then process asynchronously. |
| Desktop/local T3 or tailnet-only remote T3                   | Outbound OAuth/API access can work without public ingress. Offer clearly labeled polling-only synchronization; no real-time or webhook-delivery claim. Offline means stale, and queued status writes must be re-reviewed after reconnect.                                      |
| Local T3 behind an operator-provisioned stable public tunnel | Same signed route is possible if the tunnel actually forwards unauthenticated Linear POSTs without interactive pairing/login and preserves raw bodies. A shared T3 URL alone proves none of these properties. Sleeping local hosts still miss delivery.                        |
| Shared hosted relay with durable mailbox                     | Deferred. It would need installation/tenant routing, signature validation at arrival, authenticated outbound retrieval, retention and replay semantics. An HTTP forwarder with no durable queue does not solve offline delivery.                                               |

A browser OAuth redirect URI is not a webhook endpoint; localhost being usable for one does not make it usable for the other. Do not publish pairing tokens, localhost paths or credentials in attachments. The backlink requires a configured stable T3 URL with resource authorization after navigation; without one, keep attachment publication disabled. This research establishes no existing T3 tunnel or callback-route capability.

## Concrete failure cases and acceptance targets

These are proposed acceptance scenarios, not executed tests:

| Trigger                                                  | Required observable outcome                                                                                      |
| -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Same webhook arrives twice, then an older update arrives | One durable receipt per delivery identity; canonical refresh prevents stale payload rollback; no outbound echo.  |
| T3 status request succeeds remotely but response is lost | `outcome_unknown`, then observed-state reconciliation; no automatic stale retry or success attribution.          |
| Human writes between T3 preflight and mutation           | Residual lost-update race disclosed; any observed conflict retained; no claim of CAS protection.                 |
| Team deletes/recreates In Review under a new UUID        | Mapping attention; old command held, never remapped by name.                                                     |
| Issue moves to another team/project                      | UUID identity retained; scope/mapping attention; no copied issue or run launch.                                  |
| More than 50 issues or labels; one page fails            | Pagination completes independently; incomplete scan does not advance watermark or infer deletion.                |
| Local environment sleeps beyond retry window             | Stale sync indicator and reconnect sweep; no promise that webhook replay supplies all missed changes.            |
| Issue archived, removed, inaccessible, then restored     | Distinct source availability states; retained provenance; no plan restoration or destructive cascade.            |
| Attachment deleted in Linear                             | Publication held until explicit re-enable; do not recreate on every plan event.                                  |
| Human assignee differs from installer and app actor      | Preserve all three identities; no assignee replacement with an agent.                                            |
| Linear reaches Done while T3 delivery is Held            | Source displays Done, delivery remains Held, execution/acceptance unchanged.                                     |
| Native GitHub sync also writes status                    | Flag competing automation; default writeback hold, no cyclic GitHub→T3→Linear mirroring.                         |
| Credential refresh fails or workspace access is revoked  | Hold outbound work, preserve pending intent, surface reconnection; do not silently install under another tenant. |

Proceed to implementation only with the limited concurrency semantics above, a chosen ingress/polling deployment and approved real team UUID mappings. Runtime validation still must establish permissions, schema compatibility, signature/retry handling, archive/trash observations, pagination recovery and the visible separation of source status from plan/execution. Neither these artifacts nor the earlier design constitutes that evidence.
